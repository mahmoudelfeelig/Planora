# 3,888-activity end-to-end performance

## Workload boundary

The measured `target_case` workload is an SS23-calibrated synthetic GIU-scale
proxy with 3,888 activities, 12 weeks, 29 groups, 67 synthetic staff records,
and 35 generated rooms. It is not a direct reconstruction of the Spring 2023
timetable and is not a current institution-approved GIU dataset.

## Controlled method

The runner exercised the shared application service through both the embedded
Python transport and the HTTP API. Each measured workflow generated the
instance, serialized the request, created a session, solved, independently
validated and scored the schedule, improved it, independently validated and
scored it again, and serialized the responses. The configuration was seed 42,
four solver workers, a 20-second solve ceiling, and a 2-second / 500-iteration
improvement ceiling.

Each series used one unreported warmup followed by five fresh benchmark-client
processes. The cold-HTTP series also started a new API process per repetition;
the warm-HTTP series reused one API process and therefore exercised the real
persistent solve cache.

## Results

| Transport | Valid | Median | p95 | Maximum | Interpretation |
|---|---:|---:|---:|---:|---|
| Embedded Python | 5/5 | 17.668 s | 17.833 s | 17.850 s | Full uncached application workflow |
| HTTP, fresh API process | 5/5 | 28.080 s | 28.380 s | 28.422 s | Includes about 7.981 s API startup |
| HTTP, persistent API | 5/5 | 6.234 s | 6.498 s | 6.528 s | User-visible warm service path |

Embedded median stages were 12.105 seconds for solve, 4.039 seconds for the
Improve action, 0.591 seconds for the first score, 0.600 seconds for the final
score, and about 0.202 seconds across the two independent validations. The warm
HTTP median solve round trip was 0.341 seconds because the exact workload was
served by the shared persistent cache. Its Improve round trip was 4.234
seconds, including its own validation and before/after scoring.

Every measured run returned all 3,888 activities, zero validation errors, and
zero hard conflicts. Peak reported RSS was 250,744 KiB for embedded Python and
120,428 KiB for the persistent HTTP benchmark client; the latter does not
include the separately running API process.

## Implemented optimizations

- Weekly decomposition constructs shallow, isolated partition views instead of
  deep-copying the complete 3,888-activity instance twelve times.
- Harder weekly partitions enter the worker queue first; results are restored
  to canonical week order.
- An empty-focus Improve reuses its already validated after-score.
- Score responses rank penalty drivers from the already computed breakdown
  instead of recomputing the entire breakdown.
- Embedded, HTTP, and persistent HTTP clients all use the same
  `planora-solver-service-v1` application path.

The partition model-construction microbenchmark fell from an earlier observed
about 2.00 seconds to a 0.313-second median, approximately 6.4 times faster.
Search quality and runtime remain workload- and machine-dependent; the figures
above are measured results, not service-level guarantees.
